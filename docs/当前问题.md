## 修改计划

这些问题不应合并为一个大 change，建议拆成四个可独立验收的 OpenSpec change。

### Change A：`improve-review-console-workflow-ux`

覆盖问题：14、16、17、18、19、20。

目标：

1. 用户文案统一改为：
   - “案件” → “审核任务”
   - “审核主体” → “视频内容”
   - “不可变历史” → “审核记录”
   - “领取案件” → “开始审核”
   - “租约至” → “审核占用至”
   - “续租” → “延长审核时间”
2. 增加审核员专用预览接口。后端按 `review.read`、当前案件版本和视频状态签发短期保护媒体 URL，不复用公共 `media_url`。
3. 审核页展示机器证据来源：
   - Provider、模型版本、策略版本；
   - “测试数据 / 生产模型”来源标记；
   - 标签的中文名称和置信度说明；
   - 证据引用不可访问时显示明确提示。
4. 审核队列拆为：
   - “待我处理”：当前可领取任务；
   - “我正在审核”：当前账号仍持有的任务；
   - “最近完成”：当前审核员最近提交的决定。
5. 开始审核后自动延长占用时间；页面离开时提供“保留任务”和“放回队列”，不得静默消失。
6. 页面刷新后允许同一审核员恢复自己的进行中任务，并重新签发一次性 Lease Token，不把 Token 长期保存到 localStorage。

验收标准：

- 待审视频能在审核页播放，公共页面仍不可访问。
- 开始审核后任务立即出现在“我正在审核”。
- 刷新、关闭详情、占用过期、主动释放都有清楚状态。
- 两名审核员竞争同一任务时仍只有一人可以提交。
- 页面不再展示“案件、主体、不可变、租约”等内部术语。

### Change B：`integrate-production-moderation-provider`

覆盖问题：15。

目标：

1. 在现有 Provider-neutral 接口上接入第一个真实审核 Provider。
2. 使用耐久任务保存待推理视频、尝试次数、租约、下次重试时间和终态错误。
3. 从保护媒体生成有限数量的抽帧/音频/文本输入，限制大小和数量，不把原始媒体写入审核记录。
4. Provider 返回结果后继续通过现有内部 Machine Result API 归一化写入，不允许 Provider 直接修改视频状态。
5. 分阶段启用：

```text
只记录证据
   ↓
全部转人工
   ↓
高置信自动通过
   ↓
高置信自动拒绝
```

6. UI 必须如实标识证据来自真实 Provider、人工测试还是对账恢复。

验收标准：

- 一条新视频能自动生成真实机器标签和证据引用。
- Provider 不可用时视频保持待审，任务按有界退避重试。
- 重复回调不会产生重复 Signal 或 Decision。
- 未知标签不能导致自动通过。

待决策：

- 选择外部审核服务还是自部署模型。
- 第一阶段审核哪些模态：仅图像，或图像 + ASR/OCR。

### Change C：`add-dedicated-admin-authentication`

覆盖问题：21。

推荐边界：

```text
用户端
/auth
User Access Token
localStorage 用户会话

后台端
/admin/login
Admin Access Token
独立 AdminSessionProvider
独立存储键或 HttpOnly Admin Cookie
```

目标：

1. 新增 `/admin/login`，Admin 页面不再跳转普通 `/auth`。
2. 新增 `admin_access` Token Type 或独立 HttpOnly Admin Session Cookie。
3. `/api/admin/*` 同时要求：
   - Admin 类型会话；
   - 当前数据库账号仍为 active；
   - 当前角色具备路由声明权限。
4. Admin 会话和用户会话完全分离；在同一浏览器可同时登录普通用户和管理员。
5. 后台登录不允许自助注册，不通过前端修改角色；账号由数据库、初始化命令或后续身份提供方创建。
6. 第一阶段可以继续复用 `account` 表作为身份事实源，但登录入口、Token audience、Cookie、前端 Context 和退出流程必须独立。
7. 后续如接企业 SSO，可替换 Admin 身份提供方，不影响业务权限中间件。

验收标准：

- 普通用户 Token 即使角色 claim 被伪造也不能调用 Admin API。
- Admin 登录不会覆盖普通用户登录态。
- Admin 退出不影响用户端会话，反之亦然。
- 停用或降权立即影响已登录的 Admin 会话。
- 直接进入 `/admin/*` 时只出现后台登录页，不出现用户注册入口。

### Change D：`complete-video-lifecycle-notifications`

覆盖问题：22。

通知分层：

| 阶段 | 展示位置 | 是否耐久 |
| --- | --- | --- |
| 本地计算校验和、上传百分比 | 上传页面 | 否，前端实时状态 |
| 上传会话完成 | 上传页面 + 可选消息 | 是 |
| 视频已提交、等待审核 | 消息中心 | 是 |
| 媒体处理中/处理失败 | 作品页状态；失败进入消息中心 | 失败耐久 |
| 自动审核转人工 | 作品页显示“审核中” | 不单独通知，避免噪音 |
| 审核通过 | 消息中心 | 是 |
| 审核拒绝及原因码 | 消息中心 | 是 |
| 审核通过但媒体未就绪 | 消息中心显示“审核通过，处理中” | 是 |
| 视频最终公开发布 | 消息中心 | 是 |
| 运营下架/合规恢复 | 消息中心 | 是 |

实现原则：

1. 每种通知使用稳定 Event ID，例如：
   - `video-submitted:{video_id}:{review_version}`
   - `video-review-approved:{video_id}:{review_version}`
   - `video-published:{video_id}:{published_at}`
2. 业务事实与 Notification Outbox 同事务提交，消息发送失败不能回滚已完成审核。
3. 同一事件重复投递只生成一条 Message。
4. 消息使用结构化 `video_id`、阶段、结果和原因码，不从自然语言正文反向解析。
5. 审核通过和最终公开必须区分，避免媒体尚未完成时误导用户。
6. 上传进行中属于当前页面的瞬时反馈，不应为每个百分比写消息中心。

验收标准：

- 上传后作者收到“已提交审核”。
- 审核通过但媒体未就绪时不会显示“已发布”。
- 最终公开后收到独立发布通知。
- 拒绝、下架和恢复均带安全的用户文案和结构化原因。
- Worker 重试不会产生重复消息。

## 推荐实施顺序

```text
A 审核台体验与预览
        ↓
C 独立后台登录
        ↓
D 完整通知生命周期
        ↓
B 真实机器审核 Provider
```

说明：

- A 最先解决当前无法正常测试审核的问题。
- C 会改变 Admin 前端会话边界，应在继续扩大后台功能前完成。
- D 可在现有审核事实基础上补齐作者体验。
- B 涉及供应商、成本、隐私和模型效果，应在 Provider 选型后单独实施。
